# 儿童平板监管系统 — 需求规格与技术方案

> 版本：v1.0（需求评审稿）
> 日期：2026-09-18
> 产品代号：掌中灵

---

## 一、项目概述

一套面向家庭的安卓端儿童设备监管系统，采用 **控制端（家长手机）+ 被控端（儿童平板）+ 云端中继** 的三段式架构。

家长在控制端设定时间规则、查看使用记录、临时放行；被控端在儿童平板上强制执行、无法主动卸载或退出。**全程免 root**。

### 已确认的关键决策

| 决策项 | 结论 |
|---|---|
| 技术栈 | 原生 Kotlin（两端同一套代码库，通过 Build Variant 区分角色） |
| 管控强度 | **双模式**：设备所有者（Device Owner）与设备管理器（Device Admin），安装时由家长选择 |
| 通信方式 | 云端中继，部署在阿里云自有服务器 |
| 后端形态 | 轻量服务，Docker 单容器部署，公网 IP 直连 |
| 绑定关系 | 单家长账号可管控多台设备 |
| 规则模型 | 应用黑白名单 **叠加** 每日总时长 **叠加** 逐应用时段/单日时长上限 |
| 截屏 | 按需单张截屏 |
| 首期范围 | 核心管控 + 远程截屏 + 应用黑白名单 |

## 二、角色与核心场景

### 角色
- **家长**：控制端使用者，持有管理员密码，配置规则、查看记录、下发临时授权。
- **儿童**：被控端使用者，无法修改规则、无法卸载被控端、无法退出管控。

### 核心场景

1. **日常时长管控**：家长设定上学日每天总共 60 分钟、周末 120 分钟。儿童用满后，被控端弹出全屏提示并自动回到桌面。
2. **分应用精细管控**：家长规定「微信」仅 19:00–20:00 可用且每天最多 40 分钟；「游戏类」直接加入黑名单全天禁止。
3. **临时放行**：孩子申请多玩 20 分钟，家长在控制端点击「总时长 +20 分钟」，指令秒级下发，孩子设备立即解锁。
4. **单应用放行**：作业需要，家长对「作业帮」单独放行 30 分钟，不影响其他应用额度。
5. **查看历史**：家长查看某个 App 今天几点打开、用了多久、一天累计多少。
6. **远程查看屏幕**：家长疑似孩子偷玩，点击「查看屏幕」，被控端回传一张当前屏幕截图。
7. **防卸载防退出**：孩子尝试在设置里取消激活 / 卸载被控端，操作被拒绝或立即被家长知晓。

## 三、功能需求

### 3.1 控制端（家长手机）

#### F1. 账号与设备管理
- F1.1 账号注册 / 登录（用户名 + 密码，JWT 鉴权，支持记住登录）
- F1.2 生成配对码（6 位数字，有效期 5 分钟），在被控端输入完成绑定
- F1.3 设备列表：设备名称、型号、安卓版本、在线状态、剩余可用时长、当前前台应用
- F1.4 设备重命名、解绑（需管理员密码二次确认）

#### F2. 时间规则配置
- F2.1 **每日总时长**：分别配置「上学日（周一至周五）」与「周末（周六日）」的每日总时长（分钟）
- F2.2 **额度重置时间点**：默认每日 00:00，可自定义（如 06:00）
- F2.3 **逐应用规则**（每个 App 一条）：
  - 单日时长上限（分钟，0 = 不限制）
  - 允许使用的时段（如 19:00–20:00，支持多时段）
  - 生效星期（周一~周日多选）
  - **用时不计入当日总时长**：该应用消耗的时间不占当日额度，总时长用完后它仍可打开
  - 启用 / 停用
- F2.4 **黑白名单**：
  - 黑名单模式：列表内应用禁止使用
  - 白名单模式：仅列表内应用允许使用
  - 支持从被控端上报的已安装应用列表中勾选（带图标与应用名）

#### F3. 使用记录
- F3.1 按日期查看：每日总使用时长 + 各应用时长排行
- F3.2 时间线视图：某应用的具体打开/关闭时间点、单次时长
- F3.3 周/月趋势图
- F3.4 拦截记录：何时、因何原因（超额 / 时段外 / 黑名单）被拦截

#### F4. 临时授权（解封）
- F4.1 **总时长解封**：+N 分钟（可选 10 / 20 / 30 / 60 / 自定义）
- F4.2 **单应用解封**：指定 App +N 分钟，或临时解除其时段限制
- F4.3 **立即锁定**：一键将该设备锁定（进入锁定态，仅保留电话/紧急呼叫）
- F4.4 授权有效期：一次性（用完为止）或限时（到期自动失效）
- F4.5 **加时申请审批**：孩子端提交的"申请加时"在此汇总，支持「同意」/「修改额度后同意」/「拒绝」
- F4.6 有新申请时通过系统通知提醒家长，App 内显示角标与待办列表
- F4.7 审批结果**实时推送回被控端**，孩子无需重复申请
- F4.8 审批通过后自动生成等额 `grant`，走与家长主动授权**完全相同**的生效链路
- F4.9 可全局关闭"申请加时"功能（见策略开关 `allow_time_request`）
- F4.10 全部审批记录进入操作审计日志

#### F5. 远程操作
- F5.1 按需截屏（下发指令 → 回传当前屏幕图）
- F5.2 强制同步策略
- F5.3 查看被控端健康状态（服务是否存活、权限是否被取消）

#### F6. 安全与审计
- F6.1 管理员密码（独立于登录密码，用于退出管控 / 解绑等敏感操作）
- F6.2 操作日志：谁在什么时间做了什么配置变更

### 3.2 被控端（儿童平板）

#### F7. 首次配置向导
- F7.1 输入配对码绑定账号
- F7.2 授权引导（分步、带图文说明、可检测授权状态）：
  - 使用情况访问权限（Usage Access）
  - 无障碍服务（Accessibility）
  - 悬浮窗权限
  - 通知权限（Android 13+）
  - 电池优化白名单
  - 自启动 / 后台运行（厂商 ROM 引导页）
- F7.3 设备管理器激活（Device Admin 模式）
- F7.4 设备所有者激活（Device Owner 模式，引导家长用 ADB 完成）
- F7.5 设置管理员密码

#### F8. 管控执行引擎
- F8.1 实时感知前台应用（无障碍服务 + 使用情况统计兜底）
- F8.2 规则判定（本地执行，断网也生效）：
  - 总时长是否耗尽
  - 该应用是否在黑名单 / 不在白名单
  - 是否处于允许时段
  - 该应用单日时长是否超额
- F8.3 拦截动作：全屏遮盖层（显示原因 + 剩余可申请时间），并强制返回桌面
- F8.4 额度计算与每日重置
- F8.5 临时授权叠加生效（含有效期）
- F8.6 **申请加时入口**：拦截遮罩页提供「申请加时」按钮，孩子可选 +15 / +30 / +60 分钟并填写理由
- F8.7 提交后遮罩切换为「已发送申请，等待家长处理」，家长同意后**自动解锁**，无需孩子重试
- F8.8 申请频率限制：每小时最多 2 次、两次间隔不少于 10 分钟（防止反复骚扰家长）
- F8.9 **离线时不显示该按钮**，改为提示「当前网络不可用，请让家长在设备上输入密码」——申请加时本质上依赖网络，离线场景由离线密码承载
- F8.10 申请必须联网；若提交瞬间断网，本地缓存并在网络恢复后重发（有效期 30 分钟）

#### F9. 记录上报
- F9.1 本地记录每次应用打开/关闭会话（精确到秒）
- F9.2 定时（默认 5 分钟）与实时（应用切换时）上报
- F9.3 断网时本地缓存，联网后补传

#### F10. 防卸载 / 防退出
- F10.1 阻止自身被卸载
- F10.2 阻止自身服务被停止 / 被清理
- F10.3 检测到权限被取消或管理员被取消时，立即上报并弹窗提醒（Device Owner 模式下该操作被系统直接禁止）
- F10.4 隐藏桌面图标（可选，通过家长密码或拨号暗码唤起）
- F10.5 开机自启

#### F11. 截屏响应
- F11.1 收到截屏指令后抓取当前屏幕并上传
- F11.2 优先使用无障碍服务截屏（Android 11+，无系统录制提示）；低版本降级使用 MediaProjection（需一次性授权）

#### F13. 本地离线密码与分级解锁
- F13.1 家长在被控端本机设置 **1–3 级密码**（建议默认 3 级），各级密码互相独立
- F13.2 一级密码（日常）：总时长加时（+15 / +30 / +60 / 自定义）
- F13.3 二级密码（管理）：单应用临时放行（指定 App +N 分钟，或临时解除其时段限制）
- F13.4 三级密码（超级）：退出管控、解除设备管理器激活、卸载本应用、修改全部规则
- F13.5 隐藏呼出入口：遮罩页连续点击标题 5 次 / 长按指定区域 3 秒才出现 PIN 键盘，避免孩子发现
- F13.6 **完全离线可用**，不依赖网络
- F13.7 密码以 PBKDF2 哈希存储，绝不明文；连续错误 5 次锁定 10 分钟、10 次锁定 1 小时，联网后上报
- F13.8 支持填写密码提示语，供家长本人回忆
- F13.9 支持在线重置：设备联网时家长可从控制端重置任一级密码

### 3.3 后端服务

- F12.1 账号鉴权（JWT，Access + Refresh Token）
- F12.2 设备配对与绑定
- F12.3 策略存储与下发（长连接推送 + 拉取兜底）
- F12.4 使用记录接收、聚合与查询
- F12.5 指令队列（截屏、锁定、同步）
- F12.6 截屏图片存储与访问
- F12.7 心跳与在线状态维护
- F12.8 操作审计日志
- F12.9 **离线指令补发**：指令落库并附带有效期，被控端上线后主动拉取并执行
- F12.10 指令有效期管理：按指令类型设定 TTL，过期自动作废并在控制端呈现状态
- F12.11 加时申请的接收、推送与审批结果实时回传

## 四、双模式管控强度设计

> 这是本方案最核心的工程取舍。两条路共用同一套业务代码，仅在「权限获取与强制执行」层做策略分支。

| 维度 | 设备所有者模式（Device Owner） | 设备管理器模式（Device Admin） |
|---|---|---|
| 激活方式 | 首次装机时用电脑执行一次性 ADB 命令 `dpm set-device-owner`，或恢复出厂设置时扫码 | 平板端自助点击激活，无需电脑 |
| 阻止卸载 | **系统级禁止**，孩子无法卸载、无法取消激活 | 能阻止卸载，但孩子可在「设置→安全→设备管理应用」中取消激活后卸载 |
| 取消激活 | 系统直接隐藏入口，不可取消 | 可取消，取消时触发 `onDisabled` 回调，被控端立即弹窗 + 上报 |
| 隐藏系统设置 | 可隐藏「设置」「应用商店」等系统应用 | 仅能隐藏自身图标 |
| 锁定任务模式 | 支持，可进入 Kiosk 白名单模式，孩子完全无法跳出 | 不支持 |
| 禁用安全模式 | 支持（防通过安全模式绕过） | 不支持 |
| 适用对象 | 能防住懂技术的孩子，强度接近厂商级 | 防普通儿童足够，但对懂技术者可被绕过 |
| 附加要求 | 家长需会一次电脑操作（或用我们提供的 Windows 一键脚本） | 无 |

**产品策略**：安装向导首屏让家长选择强度等级，并显著提示差异。选择 Device Owner 时提供：
1. Windows 一键激活脚本（免命令行）
2. 图文 + 视频教程
3. 激活状态实时检测与失败原因提示

## 五、技术架构

```
┌──────────────────┐         ┌──────────────────┐
│   控制端 App      │         │   被控端 App      │
│  (Parent/Kotlin) │         │  (Child/Kotlin)  │
│                  │         │                  │
│  · 规则配置 UI    │         │  · 管控执行引擎    │
│  · 记录展示       │         │  · 无障碍服务      │
│  · 临时授权       │         │  · 前台常驻服务    │
│  · 截屏查看       │         │  · 设备管理器      │
└────────┬─────────┘         └─────────┬────────┘
         │  HTTPS REST + WebSocket     │
         └──────────────┬──────────────┘
                        │
              ┌─────────▼─────────┐
              │   阿里云轻量后端    │
              │  Node.js + Fastify │
              │  + SQLite + ws     │
              │  Docker 单容器      │
              └───────────────────┘
```

### 5.1 被控端技术栈
- 语言：Kotlin
- UI：Jetpack Compose（配置/向导页）+ 传统 View（遮盖层 Overlay）
- 架构：MVVM + Repository + Room（本地库）+ DataStore（配置）
- 依赖注入：Hilt
- 异步：Coroutines + Flow
- 网络：Retrofit + OkHttp + WebSocket
- 保活：前台服务 + WorkManager + AlarmManager（精确闹钟）
- 最低支持：Android 8.0（API 26）；无障碍截屏需 API 30+

### 5.2 控制端技术栈
- 与上基本一致，无系统级权限需求
- 图表：Compose 自绘或 Vico（周/月趋势）
- 最低支持：Android 8.0（API 26）

### 5.3 后端技术栈（轻量方案）
- 运行时：Node.js 22（LTS）
- 框架：Fastify
- 数据库：**SQLite（node:sqlite 内置模块，WAL 模式）** — 单文件、零运维、零原生依赖，单容器即可，完全满足家庭级并发的量级
- 实时通道：ws（WebSocket），按设备 ID 分房间
- 鉴权：JWT（`@fastify/jwt`）+ Node 内置 scrypt 密码哈希（免原生依赖，弃用 bcrypt）
- 文件：截屏图片存本地目录，通过带签名的临时 URL 访问
- 部署：Docker 单容器 + `docker-compose.yml`，挂载数据卷持久化 SQLite 与图片
- 预期资源占用：内存 ~80–150 MB，满足「尽量轻服务」的要求
- 反向代理：若日后有域名，加 Caddy 容器自动 HTTPS；当前 IP 直连可采用 HTTP + 应用层 AES 加密敏感字段

> 说明：为何不用 MySQL/Redis —— 家庭级场景设备数在个位数、日活请求量极低，SQLite + 内存事件总线完全够用，且省掉一整套运维负担。若未来需扩展，SQLite 可平滑迁移至 PostgreSQL。

### 5.4 通信协议设计原则
- **指令下行**：WebSocket 长连接实时推送；断线期间指令落库并带有效期（TTL），被控端重连后立即拉取补齐（详见 8.8）
- **数据上行**：使用记录批量 POST；心跳 30 秒一次
- **断网可用**：被控端本地持有完整策略副本与本地计时器，规则判定完全本地化，云端仅做配置同步与记录汇总
- **离线自救**：断网时家长可用被控端本机的分级密码完成加时、应用放行与退出管控（详见 8.9）
- **幂等**：所有指令带 `commandId` 与单调递增序号，被控端按序号执行并去重

### 5.5 服务器地址与配置管理（可配置设计）

**核心原则：服务器地址绝不硬编码在代码里**，分三层覆盖，任何时候换服务器、加域名、切 HTTPS 都无需改动业务代码。

| 层级 | 位置 | 修改方式 | 适用场景 |
|---|---|---|---|
| ① 编译期默认值 | `gradle.properties` → `BuildConfig` | 改一行重新打包 | 设定团队/发布默认服务器 |
| ② 运行期覆盖 | App 内 DataStore | 页面输入，**无需重新打包** | 换服务器、临时指向测试环境 |
| ③ 配对时写入 | 被控端配对页 | 家长首次配置时填写 | 被控端装机 |

优先级：**③ 配对写入 > ② 运行期覆盖 > ① 编译期默认值**

#### 当前服务器配置

> 下列地址为 **RFC 5737 文档专用示例地址**（`203.0.113.0/24`），仅用于说明格式。
> 真实部署地址不写入代码库，而是放在不入库的 `android/local.properties` 与本机 `deploy/.env` 中。

```
主机    ：203.0.113.10（示例）
端口    ：8111（服务端对外端口，REST API 与 WebSocket 共用；容器内仍监听 8080）
协议    ：HTTP（暂无域名；日后加域名或证书只需改配置）
```

#### Android 端：编译期默认值

```kotlin
// 取值顺序：android/local.properties（本机私有，优先）→ android/gradle.properties（示例值）
// gradle.properties
// SERVER_HOST=203.0.113.10
// SERVER_PORT=8111
// SERVER_SCHEME=http

android {
    defaultConfig {
        buildConfigField("String", "DEFAULT_SERVER_HOST",
            "\"${serverProp("SERVER_HOST", "203.0.113.10")}\"")
        buildConfigField("int", "DEFAULT_SERVER_PORT",
            serverProp("SERVER_PORT", "8111"))
        buildConfigField("String", "DEFAULT_SERVER_SCHEME",
            "\"${serverProp("SERVER_SCHEME", "http")}\"")
    }
    buildFeatures { buildConfig = true }
}
```

#### Android 端：运行期覆盖

```kotlin
data class ServerConfig(
    val host: String,
    val port: Int,
    val scheme: String,                 // http | https
    val trustSelfSigned: Boolean = false // 自签证书场景预留
) {
    val baseUrl: String
        get() = "$scheme://$host:$port/api"
    val wsUrl: String
        get() = (if (scheme == "https") "wss" else "ws") + "://$host:$port/ws"
}
```

- 存放在 DataStore Preferences，与 token 同级管理
- **主机（host）与端口（port）是两个独立输入框，均可自由配置**——主机支持 IP 或域名，端口支持 1–65535 任意值，代码中不存在任何写死的地址或端口
- 保存前做校验：主机非空且格式合法、端口在 1–65535 范围内，然后请求 `/api/health` 做连通性探测
- `ws://` / `wss://` 由 `scheme` 自动推导，不单独配置
- 若填了域名 + HTTPS，`trustSelfSigned` 保持 `false` 即可走标准证书校验

#### 设置入口设计（两端一致）

- **控制端**：登录页底部「服务器设置」文字按钮
- **被控端**：主界面顶栏设置图标 + 配对页「服务器设置」文字按钮（可见入口；隐藏式入口仅用于离线密码，服务器设置需要明示才能在换服务器时被家长找到）
- 输入框需做连通性检测：保存前先请求 `/api/health`，失败给出明确原因（超时 / 拒绝连接 / 端口错误）
- 切换服务器后**清除本地 token 与全部缓存**，强制重新登录或重新配对
- 提供「恢复默认」按钮回到 `BuildConfig` 中的默认值

#### 后端：全部走环境变量

`deploy/.env`

```

JWT_SECRET=<部署时随机生成>
DB_PATH=/data/app.db

# 指令有效期（秒）
COMMAND_TTL_SCREENSHOT=60
COMMAND_TTL_UNLOCK=21600

# 离线密码错误限流
```

`docker-compose.yml` 通过 `env_file: .env` 注入，镜像内不写任何服务器地址常量。

#### 部署注意事项

1. **阿里云安全组需放行 TCP 8111**（入方向，默认对外端口），否则 App 无法连接。
2. 端口随时可配：服务端改 `.env` 的 `APP_PORT`，App 端在「服务器设置」里同步改端口（主机与端口是两个独立可配置项，运行期覆盖编译期默认值，无需重新打包）。
3. 数据卷挂载 `/data`，持久化 SQLite 数据库与截屏图片；**容器重建不丢数据**。
4. IP 直连走 HTTP 时，密码、截屏等敏感数据在**应用层用 AES-256-GCM 二次加密**，不完全依赖传输层。
5. 日后接入域名：申请域名 + Caddy 自动签发 Let's Encrypt 证书 → 只需把 App 端 `scheme` 改为 `https`、`host` 改为域名，**业务代码零改动**。

## 八、被控端核心机制详解

### 8.1 前台应用感知
- **主通道**：`AccessibilityService` 监听 `TYPE_WINDOW_STATE_CHANGED`，从 `event.packageName` 取前台包名，实时性最好（毫秒级）
- **兜底通道**：`UsageStatsManager.queryEvents()` 轮询（1 秒），应对无障碍被系统回收
- **过滤**：忽略 `com.android.systemui`、自包名、输入法等系统组件

### 8.2 时长统计（精度关键）
不依赖 `queryUsageStats` 的粗粒度聚合，而是**自己按事件流精确计算**：
- 前台切到 A → 记录 A 的 `start_ts`
- 前台从 A 切走 / 熄屏 / 关机 → 记录 A 的 `end_ts`，累加 `duration_ms`
- 熄屏、锁屏、系统弹窗期间**暂停计时**（`BroadcastReceiver` 监听 `ACTION_SCREEN_OFF/ON`）
- 按 `reset_hour` 归日，生成 `day_key`

### 8.3 拦截动作
1. 判定命中 → 立即用 `WindowManager` 添加 `TYPE_APPLICATION_OVERLAY` 全屏遮罩
2. 遮罩显示：拦截原因、今日剩余时长、可申请按钮（可配置是否允许孩子"申请加时"）
3. 同时调用 `performGlobalAction(GLOBAL_ACTION_HOME)` 强制回桌面
4. Device Owner 模式下可进一步禁止该应用启动

### 8.4 保活策略（分级递进）
1. 前台服务 + 常驻通知（Android 14 声明 `foregroundServiceType`，建议 `specialUse` 并说明用途）
2. 引导加入电池优化白名单（`REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`）
3. `AlarmManager.setExactAndAllowWhileIdle` 精确闹钟，每 1–5 分钟自唤醒校验
4. `WorkManager` 周期任务做二次唤醒
5. 双进程/多组件互拉（`Service` + `JobService` + 广播监听）
6. `BOOT_COMPLETED` 开机自启
7. 针对小米/华为/OPPO/vivo 提供厂商白名单引导页
8. Device Owner 模式下可设置应用为 `setPersistentPreferredActivity` / 免于省电策略

### 8.5 防卸载 / 防退出
- Device Owner：`setUninstallBlocked(this, packageName, true)` + 隐藏设置入口 + `addUserRestriction(DISALLOW_SAFE_BOOT)`
- Device Admin：`setUninstallBlocked` + `DeviceAdminReceiver.onDisabled()` 回调立即弹窗上报 + 管理员密码保护
- 隐藏桌面图标：`PackageManager.setComponentEnabledSetting` 禁用 launcher 入口，家长用暗码唤起
- 退出管控需管理员密码，多次错误锁定

### 8.6 截屏实现
- **优先**：`AccessibilityService.takeScreenshot()`（API 30+）— 无需 MediaProjection 授权，无录屏弹窗
- **降级**：`MediaProjectionManager`（需一次性授权，Android 14+ 每次会话都需授权）
- 上传前压缩为 JPEG（质量 60，最长边 1280），减小流量

### 8.7 规则引擎（本地执行）
```
判定顺序（任一命中即拦截；顺序不可调整）：
0. 家长点了「立即锁定」               → 拦截 (lock)      ← 压过管控总开关
1. 处于「临时总解封」有效期内          → 放行
2. 管控总开关关闭                     → 放行
3. 该应用在黑名单模式列表内            → 拦截 (blacklist)
4. 白名单模式下该应用不在白名单内       → 拦截 (not_in_whitelist)
5. 总时长已耗尽（含加时额度）          → 拦截 (total_exhausted)
     ↳ 标了「用时不计入当日总时长」的应用跳过本条
6. 该应用单日时长已超额                → 拦截 (app_exhausted)
7. 当前不在该应用允许时段内            → 拦截 (out_of_window)
8. 否则放行
```

两条最容易改错、因此也写进了代码注释的顺序决定：

- **黑白名单排在总时长之前**：「这个应用根本不许用」应当压过「今天还有额度」。
- **「立即锁定」排在管控总开关之前**：家长按下锁定时要的是立刻生效，「管控已暂停」不该成为例外。

**「用时不计入当日总时长」（`exempt_total`）的边界**：它**只**跳过第 5 条。该应用的用时
不计入当日已用总量，所以总时长耗尽后它仍然打得开；但第 3/4 条（名单）与第 6/7 条
（它自己的单日上限与允许时段）照旧生效 —— 于是它不会退化成「无限使用」。

被控端统计「今日已用」时会整段剔除该应用的会话（含进行中的那段），
服务端的报告接口用**同一套口径**（`exempt_total` 且当天在生效星期内才算），
两端不会出现「家长看到的剩余额度和设备实际执行的不一致」。

所有判定使用**本地策略副本 + 本地计时器**，断网完全可用；联网时接收策略增量更新。

### 8.8 离线指令补发机制

**设计目标**：家长在任何时刻下发的指令都不丢，被控端上线后自动补齐执行；同时避免"过期指令"造成错误效果（例如 2 小时前的截屏请求现在才到达）。

#### 指令分类与有效期（TTL）

| 指令类型 | 语义 | 默认有效期 | 过期处理 |
|---|---|---|---|
| `sync` / 策略变更 | 同步最新策略 | 永久（直到执行） | — |
| `lock` | 立即锁定（持续状态） | 永久 | — |
| `unlock` | 解除锁定 | 6 小时 | 丢弃（避免意外解锁） |
| `grant`（加时 / 放行） | 授予额度 | 24 小时 | 丢弃，控制端提示"已失效" |
| `screenshot` | 抓取当前屏幕 | **60 秒** | 丢弃（截图过时即无意义） |

各类型 TTL 在后端配置，可按需调整。

#### 补发流程

1. 控制端下发 → 后端写入 `commands` 表：`status=pending`、`expire_at = now + TTL`，`id` 单调递增并作为执行序号
2. 若被控端在线 → 经 WebSocket 立即推送，`status` 置 `sent`
3. 若被控端离线 → 指令停留在 `pending` 等待
4. 被控端**每次 WebSocket 连接建立后（`onOpen`）的第一件事**：`GET /api/devices/{id}/commands?status=pending` 拉取全部待执行指令
5. 被控端按 `id` **升序**逐条校验：
   - `expire_at` 为空，或 `now <= expire_at` → 执行
   - 已过期 → **不执行**，回报 `expired`
6. 每条执行后回报 `POST /api/devices/{id}/commands/{id}/ack`，携带 `done | failed | expired`
7. 被控端本地维护「已执行指令 ID 台账」（保留 7 天），保证重复推送时**幂等**、不重复执行

#### 顺序与冲突规则

- 严格按 `id` 升序执行，保证"先加时、后锁定"这类组合的语义正确
- `grant` 之间为**叠加**关系，不互相覆盖
- 同类状态型指令（如两条 `lock`）以最后一条为准
- **策略类指令只保留最新一版**：后端下发新策略时，直接覆盖旧的 pending 策略指令，避免拉取到历史版本

#### 离线期间的额度追溯问题（重要取舍）

被控端离线期间仍会按本地规则正常管控（该拦就拦）。上线后补发的 `grant` **从生效时刻起算，不回溯补贴**离线期间"本该享有的额度"。

原因：回溯会让家长误判实际效果，也给孩子留下可乘之机（故意断网攒额度）。控制端界面需明确提示：**"该指令将在设备上线后生效"**。

### 8.9 本地离线密码体系

**为什么必须做**：管控类 App 的核心场景恰恰是"断网"和"家长临时要放行"。若解锁只能走云端，一旦家里网络故障或平板在外无信号，家长将完全失去控制权。

#### 分级设计（默认 3 级，可精简为 1–2 级）

| 级别 | 名称 | 可执行操作 | 需联网 |
|---|---|---|---|
| L1 | 日常密码 | 总时长加时：+15 / +30 / +60 / 自定义分钟 | 否 |
| L2 | 管理密码 | 单应用临时放行：指定 App +N 分钟，或临时解除其时段限制 | 否 |
| L3 | 超级密码 | 退出管控模式、解除设备管理器激活、卸载本应用、修改全部规则 | 否 |

#### 输入方式（1.0.1 变更：内联输入）

~~拦截遮罩页上设三个隐藏入口~~（连点标题 / 长按右下角 / 拨号暗码）——
真机验证发现两条硬伤：入口难发现，且独立密码 Activity 会被
`TYPE_APPLICATION_OVERLAY` 遮罩压住不可见。**已改为**：

- 密码输入框**直接显示在拦截遮罩页上**，验证通过后在同一页展开操作按钮
  （加时档位 / 放行当前应用 / 退出管控二次确认），不再弹出独立界面
- 验证与限流逻辑不变（PinStore 本地校验，断网可用）

#### 安全约束

- 哈希算法：**PBKDF2-HMAC-SHA256**，迭代 ≥ 100,000 次 + 每级独立随机盐，绝不明文存储
- 错误限流：连续错误 5 次 → 锁定 10 分钟；10 次 → 锁定 1 小时；锁定期间入口不可用
- **所有输入尝试（含失败）在联网后上报**，家长可看到"孩子曾试图破解密码"的记录
- 设置时强制提示：三级密码不得与一、二级相同，不得使用生日、连续数字等弱口令

#### 忘记密码的风险与后路（必须让家长知情）

- **设备联网时**：家长可从控制端远程重置任一级密码，无需设备操作
- **完全离线且完全忘记**：只能通过恢复出厂设置
- **因此建议**：Device Owner 模式下**默认不启用** `DISALLOW_FACTORY_RESET`（保留"恢复出厂"这条后路），除非家长明确知晓风险并主动选择禁用
- 设置密码时提供「密码提示语」字段；密码哈希可**加密备份**至云端，用于更换设备时恢复同一套密码

### 8.10 加时申请与审批流程

**定位**：给孩子一个"正当申请"的出口，避免孩子为了多玩而尝试破解密码或强行卸载。同时把决定权牢牢留在家长手里。

#### 完整链路

1. 被控端命中拦截规则 → 遮罩页显示拦截原因与今日已用时长
2. 遮罩页底部提供「申请加时」按钮（受策略开关 `allow_time_request` 与频率限制控制）
3. 孩子选择时长（+15 / +30 / +60 分钟）并可填写理由，提交至后端
4. 后端写入 `time_requests`（`status=pending`），**有效期 30 分钟**，同时通过 WebSocket 推送至控制端
5. 控制端弹出系统通知 + App 角标，家长打开待办列表
6. 家长三选一：**同意** / **修改额度后同意**（如孩子申请 60 分钟，家长只批 20 分钟）/ **拒绝**
7. 后端写入审批结果 → WebSocket 实时推回被控端
8. 通过 → 按 `decided_min` 生成 `grant`，被控端立即解锁；拒绝 → 遮罩保持，孩子可稍后再次申请（受频率限制）

#### 关键设计点

- **审批通过复用 `grant` 链路**：与家长主动授权走同一套生效机制，不额外实现一套逻辑，保证额度叠加、有效期、本地持久化行为完全一致。
- **家长可"打折"批准**：这是最常用的操作——孩子申请 60 分钟，家长给 20 分钟，避免"要么全给要么全不给"的僵局。
- **申请必须联网**：申请本质是双向通信。离线时按钮不显示，改提示使用设备上的离线密码（详见 8.9）。这样两条自救通道形成互补——
  - 有网：孩子申请 → 家长远程审批
  - 断网：家长在设备上直接输密码
- **防骚扰**：每小时最多 2 次、间隔 ≥ 10 分钟；申请 30 分钟未被处理自动过期，避免孩子第二天看到昨天的旧申请。
- **防"卖惨"轰炸**：控制端同一设备的多个待审申请会折叠展示，家长不会被打扰。

> **实现补充（M4 已落地）**
> - 申请入口只对**额度类与时段类**拦截开放（总时长用尽 / 该应用时长用尽 / 不在允许时段）。
>   名单命中与家长主动锁定**不给入口** —— 那是家长的明确决定，开放申请等于把它降级成可谈判项。
> - 申请范围由拦截原因决定：总时长用尽申请的是「加时」，应用时长/时段问题申请的是「放行该应用」。
>   用错范围的话家长批了也不会生效。
> - 孩子端不选择时长，统一申请 30 分钟；家长批准时可打折。少一层交互，孩子不会因为
>   纠结"报多少"而反复提交。
> - 幂等：同一范围同一应用已有待审申请时复用，不新建、也不再通知家长，且**不消耗申请额度**。

### 8.11 两套下行走廊：指令队列与临时授权

这是 M4 引入的核心区分。两者**不能混用**，混用会产生语义错误。

| | 指令队列 `commands` | 临时授权 `grants` |
|---|---|---|
| 语义 | 一次性**动作** | 持续**状态** |
| 内容 | 立即锁定、解除锁定、按需截屏、请求重报应用清单 | 加时、单应用放行、临时总解封 |
| 下发 | **先落库再推送**；设备上线拉取补执行 | **整份对账**（`GET /api/device-state`）+ 实时推送 |
| 失效 | 每条带 TTL，过期置 `expired` 并在控制端回显为「已失效」 | `expire_at` 自然淘汰 |
| 回执 | 有；按 `commandId` 幂等，**已终态不被覆盖** | 无（状态本身就是真相） |

**为什么授权不做成指令**：授权是有有效期的持续状态。逐条下发会出现
「补发的授权到达时早已过期」这种无法自洽的情形 —— 家长 3 小时前批准了 30 分钟，
设备现在才上线，到底给不给？对账天然没有这个问题：设备拿到的就是"此刻仍生效的那些"。

**为什么对账还要配 `stateVersion`**：撤销与新增两个推送可能乱序到达。
被控端只在 `stateVersion >= 本地版本` 时应用整份状态，本地由指令驱动的
`setLocked` **不动版本号**，因此旧状态永远覆盖不了新状态。

#### ★ 上线流程的固定顺序（错一次就是线上事故）

```
拉策略 → 补执行离线指令 → 设备状态对账
                            ↑ 权威状态必须最后落地
```

反例：设备离线三天，家长中途「锁定」过又「解除」了。`immediate_lock` 永久有效，
`clear_lock` 6 小时后过期 —— 重新上线时只有锁定那条会被补发执行。
如果顺序颠倒（先对账再补执行），设备会被那条陈旧的锁定指令永久锁住，
而家长界面显示的是"未锁定"。让对账最后执行，才能把设备恢复成家长真正想要的状态。

#### 三种授权范围的准确语义

| 范围 | 效果 | 边界 |
|---|---|---|
| `total_add` 加时 | 增加当日总时长上限 | 绑定额度日，跨过归日点自动失效 |
| `app_allow` 单应用放行 | 该应用不受黑白名单与逐应用规则限制 | **仍受当日总时长约束** |
| `unlock` 临时总解封 | 有效期内完全关闭管控 | 压不过「立即锁定」；最长 12 小时 |

还有一条**不属于临时授权**的常设规则项：逐应用规则里的「用时不计入当日总时长」
（`exempt_total`）。它与 `app_allow` 互补而非重复（对照表见 8.7）：

- `app_allow` 是**临时的**，管「现在能不能用」，会绕过黑白名单；
- `exempt_total` 是**常设的**，管「用了算不算数」，不绕过名单。

需要「长期网课不受限」用后者；需要「今天临时放行一小时」用前者。

`app_allow` 不豁免总时长是刻意的取舍：家长批一个"放行微信"，本意是让它能用，
而不是变成全天随便玩。需要无限使用时应当同时加时 —— 两件事分开表达，
家长的选择才是准确的。

## 十、APK 签名、分发与安装

### 10.1 直接回答：安卓 App 需要证书吗？

**需要「签名」，但不需要花钱买证书。** 这是三个最容易被混为一谈的"证书"，务必分清：

| 概念 | 是否必须 | 费用 | 用途 |
|---|---|---|---|
| **APK 签名证书**（keystore） | ✅ 必须 | 免费，自己生成 | 证明 APK 来源与完整性；系统安装 release 包时强制校验 |
| **HTTPS / TLS 服务器证书** | 视情况 | Let's Encrypt 免费或自签 | 加密 App 与服务器之间的通信 |
| **上架商店的资质证书** | 本项目不需要 | — | 软著、企业资质等，仅上架应用商店才需要 |

### 10.2 三种场景下的具体要求

1. **开发调试阶段 —— 完全不需要额外配置。**
   Android Studio 会用自动生成的 debug keystore 签名，直接 `Run` 或导出 debug APK 都能安装。

2. **正式使用（release 包）—— 必须签名，但用的是自签名证书。**
   未签名的 release APK 安装时会被系统以 `INSTALL_PARSE_FAILED_NO_CERTIFICATES` 拒绝。所谓"证书"用 JDK 自带的 `keytool` 自己生成即可，**不需要向任何机构申请，也不需要付费**。

3. **上架应用商店 —— 本项目不做。**
   采用**侧载（家长手动安装 APK）**分发方式，因此不需要软件著作权、不需要开发者账号、不需要任何付费证书。

### 10.3 keystore 管理（最容易踩的坑）

- **同一个应用的所有后续版本，必须使用同一个 keystore 签名。** 否则无法覆盖升级，会报签名冲突，必须卸载重装——而被控端被设为不可卸载时，这个错误会非常麻烦。
- 建议有效期设为 **25 年以上**（Google Play 要求至少到 2033 年）。
- 务必备份 keystore 文件与密码，**丢失后无法找回**，只能换包名重新发布。
- 本项目做法：生成统一 release keystore（`zhangzhongling.jks`），控制端与被控端 APK 共用；签名配置写入 `build.gradle.kts`，密码通过 `local.properties` 或环境变量注入，**不提交到 Git**。

### 10.4 侧载安装会遇到的三个真实坑（必须写进安装指南）

**坑 1 — "允许安装未知应用"**
Android 8.0+ 改为按来源授权。家长首次安装时需在系统提示中允许对应来源安装应用。

**坑 2 — Google Play Protect 报风险**
本应用会申请无障碍服务 + 读取应用列表权限，Play Protect 很可能弹出"此应用可能有害"。需引导家长选择「仍然安装」，必要时在该设备的 Play Protect 设置中关闭扫描。这是所有管控类 App 的常态，不是我们的问题。

**坑 3 — Android 13+ 的「受限设置」（Restricted Settings）★ 最容易被卡住**
Android 13（API 33）起，**从非官方商店侧载的应用，默认不允许开启无障碍服务与"使用情况访问"权限**。家长点击开关时系统会直接禁止并提示"出于安全考虑，此设置当前不可用"，看起来像软件坏了。正确解法：

> 设置 → 应用 → 掌中灵（被控端）→ 右上角 ⋮ → **允许受限设置** → 然后再开启无障碍服务

这一步必须在被控端安装引导中**显著提示并给出截图指引**，否则家长会卡死在这一步。

**补充：厂商 ROM 额外设置**
小米 / 华为 / 荣耀 / OPPO / vivo 等 ROM 还需额外设置「自启动」「后台运行白名单」「省电策略 → 无限制」，否则前台服务会被系统杀掉。安装引导需按机型给出对应路径。

2. 精确闹钟（`GuardKeepaliveAlarm`，`SCHEDULE_EXACT_ALARM`）
3. WorkManager 周期任务（`GuardKeepaliveWorker`，15 分钟下限）

三者互补：精确闹钟在部分 ROM 被限制，WorkManager 在部分 ROM 被延迟，一起用才稳。另有 `GuardBootReceiver` 开机自启、`onTaskRemoved` 重启、设备管理器 `onDisabled` 回调立即弹窗+上报。

**厂商白名单引导**：识别小米/华为/荣耀/OPPO/vivo/三星/一加/魅族，给出各自的自启动与后台限制设置路径；`KeepaliveManager.snapshot()` 输出保活健康度（前台服务、电池优化豁免、精确闹钟、厂商白名单四项），家长与被控端都能看到缺哪项。

**密码存储与同步的三条硬约束**
1. 只存 PBKDF2-HMAC-SHA256 哈希（12 万次迭代、每级独立 16 字节随机盐），明文不落盘
2. **每次改密码必换新盐** —— 复用旧盐会让"改了密码"在哈希层面毫无变化
3. **本地 + 云端双写**，本地保断网可用、云端保换机可恢复；冲突用单调递增 `version` 解决，**只有云端版本更高才覆盖本地**（否则家长刚在设备上改的密码会被陈旧备份冲掉）

**离线密码能力**：断网时可用 L1 加时、L2 放行、L3 退出；错误限流 5 次锁 10 分钟、10 次锁 1 小时，失败尝试本地落库并在联网后上报，家长能看到"孩子试过破解"。

### 唯一建议你留意的一个风险口

第 10 条——Device Owner 模式下不禁用「恢复出厂设置」。这意味着孩子理论上可用"恢复出厂"彻底摆脱管控（代价是平板数据全部清空）。我保留它，是为了避免家长忘记离线密码后设备变成"砖"。若你判断这个口子必须堵上，告诉我，我改为默认禁用 `DISALLOW_FACTORY_RESET`，但请务必确保家长牢记离线密码。
